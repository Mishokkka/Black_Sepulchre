# Аудит Black Sepulchre — 4 октября 2026

Проверены клиент React, серверный движок, рабочая база Supabase, SQL/RLS, переходы для двух сторон и домашние правила 2.2.1 из четырёх Markdown-документов этого репозитория. Основная архитектура подходит для двух игроков: сервер рассчитывает команду, Postgres атомарно сохраняет версию и квитанцию, клиент получает проекцию своей стороны. Переписывать приложение или переносить базу не требуется.

## Проверка

- 96 тестов: исходные 73 и 23 дополнительные проверки. Покрываются стратегия, составы, таймеры, миссии, кризис, весь график до финального боя, исправление результата, идемпотентность и новые регрессии.
- SQL проверен в PGlite с настоящими миграциями и исходниками работающих create/join RPC. Два разных аккаунта занимают разные стороны; повторный join идемпотентен; третий и посторонний получают отказ; анонимный вызов закрыт.
- `npm run build`: TypeScript и production bundle проходят. Остаётся предупреждение о крупном основном JS-файле: примерно 1.24 MB / 233 KB gzip.
- `npm audit --omit=dev`: известных уязвимостей не найдено на дату проверки.
- В браузере проверены пустая цель, экран Logistics и исправление Result вторым игроком с повторным подтверждением первым. Тестовые действия выполнялись в DEV demo, отдельно от рабочей кампании.
- В рабочей базе проверены ACL, RLS, SECURITY DEFINER, закрытая схема, публикация Realtime, применённая история миграций и целостность состояния. После миграции остались те же версия 11, фаза setup, один участник и 11 квитанций команд. Игровые данные не пересчитывались.

## Что означает соответствие правилам

Проверен домашний регламент **2.2.1**, а не автоматически обновляемый официальный баланс Warhammer. Генератор проверяет наличие 33 карточек миссий, 36 событий D66, 30 Honours и 24 Scars; это проверка полноты таблиц, а не доказательство всех комбинаций правил.

Сохранено существующее продуктовое решение: общий каталог применяется без отдельной подписи второго игрока. Это упрощение относительно строгой процедуры Snapshot в справочнике 2.2.1 уже описано в README. Объявленный бой по-прежнему использует зафиксированные данные; обе подписи на Result и Aftermath обязательны. Если нужен буквально строгий режим Snapshot, его лучше сделать отдельной настройкой кампании.

Положение моделей, LOS, eligibility, натуральные боевые броски и выполнение Deeds по-прежнему подтверждают игроки. Приложение не получает их с реального стола. Официальная актуальность всех datasheets/points импортированного каталога этим аудитом не сертифицирована. Необходимость этих фактов не является ошибкой расчётного движка.

Полный вход двух реальных аккаунтов в production и реальная настольная партия не проводились: в рабочей кампании пока зарегистрирован один участник. Сценарии второго пользователя проверены SQL-тестами и переключением сторон в demo. Это ограничение проверки, а не утверждение о поломке второго аккаунта.

## Состояние Supabase

После миграции Performance Advisor больше не сообщает о двух отсутствующих индексах и построчном вызове auth.uid в исправленных политиках. Сообщения о неиспользуемых индексах ожидаемы для маленькой новой базы; удалять индексы ограничений/связей на этом основании не следует.

Три private-таблицы с RLS без клиентских policies намеренно закрыты для клиента. Два доступных authenticated SECURITY DEFINER RPC — create/join — проверены как точки входа. Не надо открывать private-схему, чтобы убрать информационное сообщение Advisor. [Пояснение Supabase про RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

Остаётся настройка Auth: проверка паролей по базе утечек отключена. Рекомендую включить её, если она доступна на вашем плане. Это изменение настройки аккаунтов, оно не входило в исправление кампанийных данных. [Настройка защиты паролей](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).

Репозиторий содержит миграции нового движка, но не полную старую историю 2.0–2.1. Для переноса в пустой проект нужна базовая схема или отдельно проверенный экспорт истории. Текущая рабочая база не требует reset; выполнять его нельзя как способ установки этих исправлений.
