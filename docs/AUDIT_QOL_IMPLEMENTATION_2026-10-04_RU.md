# Проверка внешнего аудита и внедрение QoL — 4 октября 2026

Проверен предоставленный владельцем файл `Black_Sepulchre_AUDIT_2026-10-04_RU.md`. Это оценка его выводов и журнал соответствующих изменений, а не новая редакция правил.

## Что подтвердилось

- PR #11 уже объединён в `main`. В рабочей базе `anon` не имеет доступа к таблицам кампании; у `authenticated` остался только SELECT для `campaigns`, `campaign_members`, `campaign_versions`. USAGE на `campaign_private` отсутствует у обеих клиентских ролей.
- DEFAULT `campaigns.rules_version` действительно равен `2.2.1`. Эти исправления повторно применять не требуется. В журнале рабочей базы они имеют другие временные номера, чем одноимённые SQL-файлы в репозитории; проверено фактическое состояние прав и DEFAULT.
- Предупреждения о доступных SECURITY DEFINER RPC относятся к двум намеренно публичным операциям создания/входа. Вызовы проверяют авторизацию и членство; закрывать эти RPC только ради исчезновения предупреждения не нужно.
- Отсутствие клиентских политик у закрытых таблиц `campaign_private` соответствует их назначению. Клиент читает подготовленную сервером проекцию состояния.
- Большой начальный JS действительно связан с импортами через тяжёлый `CampaignViews` и зависимостью очистки черновиков от всего валидатора Muster, который подтягивал справочник юнитов.

## Где формулировки аудита требуют уточнения

«Критических воспроизводимых расхождений не найдено» — результат перечисленных проверок, а не доказательство отсутствия ошибок во всех комбинациях. Небольшая рабочая кампания и спокойные логи сами по себе не проверяют одновременную игру двух аккаунтов.

Членство второго игрока не означает, что он сейчас онлайн. Для такого утверждения понадобилась бы отдельная Presence-механика. Здесь показывается только факт присоединения, с учётом свежести последней проверки.

Оффлайн сохраняются **черновики Muster и отчёта**. Стратегические команды не ставятся в очередь: им нужен сервер, который проверит фазу, ресурсы и актуальную версию. Поэтому предложенное сообщение «решения сохраняются локально» заменено точным описанием возможностей.

Подключение Realtime не является условием начала кампании. При его недоступности сохраняется резервная проверка каждые 30 секунд, при фокусе и возвращении сети. Нужна видимость этого режима, а не дополнительная галочка допуска к игре.

Дополнительно устранена потеря идентификатора неопределённой отправки при обновлении страницы. Такой запрос сохраняется в `sessionStorage` отдельно для аккаунта и кампании; после перезагрузки отправляется тот же requestId и expectedVersion. Повтор после потерянного ответа не создаёт вторую команду. При истечении сессии во время проверки запись сохраняется для повторного входа этим же аккаунтом. Успех либо окончательный отказ удаляют запись.

Основной минифицированный JS: **1 397,35 → примерно 334 КБ**; gzip **276,90 → примерно 104 КБ**. Это размер основного файла, не всего приложения. Полный справочник карточек остаётся крупным отдельным отложенным модулем; дальнейшее разделение карточек можно оценить после измерения загрузки каталога на телефоне. Предупреждение Vite о размере этого отложенного модуля не скрыто.

## Как устроена проверка браузером

`npm run test:e2e:prepare` создаёт изолированную конфигурацию внутри игнорируемой `tmp/e2e-stack`, применяет совместимую старую тестовую схему и текущие миграции. Требуется работающий Docker. `npm run test:e2e` запускает текущую Edge Function, собирает приложение с локальным URL и запускает Chromium.

Тест создаёт два временных аккаунта настоящего локального Auth. Через интерфейс создаёт кампанию, присоединяет второго командира и проверяет одновременные отметки готовности. Одна привилегированная тестовая операция помещает эту кампанию в окно Recon Lock, после чего решения вновь идут через настоящий UI → Auth → Edge → Postgres.

Проверяются скрытый выбор первого игрока до второго решения, совпадение раскрытых данных, одна общая версия после перезагрузки, оффлайн-индикатор. Отдельно теряется ответ **после реального успешного commit**: обновление страницы и проверка отправки должны повторить исходный UUID, получить replay и не увеличить версию повторно. Ошибки выполнения браузера завершают тест неудачей.

Это проверяет актуальный сетевой путь и конкурентную запись, но не воспроизводит всю историческую SQL-схему рабочего проекта и не заменяет тесты всех миссий. Проверка совместимости тестовой схемы со всеми текущими миграциями также включена в обычный набор тестов.

## Что оставлено вне этого изменения

Защита от утекших паролей действительно отключена в Auth Advisor. Это настройка Auth, доступность которой зависит от тарифа; она не требует изменения механик кампании. См. [документацию Supabase](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).

INFO об unused indexes на маленькой базе не даёт достаточных оснований удалять индексы. Старый литерал `rules_version: 2.0` в историческом create-аудите имеет P3 и не влияет на серверный движок или отображаемую версию; исправление старого API лучше включить в отдельное упрощение create-пути.
